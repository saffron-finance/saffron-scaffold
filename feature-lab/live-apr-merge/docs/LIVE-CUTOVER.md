# Release verification and cutover

The public interface is the combined Home, Portfolio and Live APR build in this
package. Serve it with the canonical `liquidity-incentives` backend. The earlier
incentives frontend remains an internal validation interface.

## Release identity

`npm run build:live` writes `dist-live/`. Default and lab builds write `dist/`
and use the same wallet/API implementation. Live appearance controls can be enabled with
`VITE_UI_TWEAKS=true`; they never choose the payment adapter.

Every build writes `deployment-mode.json` after its HTML, Vite manifest and lazy
assets are complete. It records application/mode, base path, version, Git revision,
source digest, clean-source status, exact file hashes and an asset-inventory hash.
The source ZIP's `source-manifest.json` identifies the same source. The guide's
version comes from its model; its generated bytes are included in both identities.
ZIPs are separately verified downloads and are not recursively hashed as assets.

These hashes detect partial or mixed publication. They are not signatures or a
substitute for trusted hosting access. Supply the approved source manifest to
pin the expected release, rather than trusting whichever marker the host serves.
Build public settings and platform output can change asset hashes without
changing source identity; preserve the actual build and its marker together.

## Configure with intake closed

- Supply real campaign terms, operator identities, service coverage, protocol
  configuration, protected RPC access and an independent database. Use the
  existing Campaigns UI for catalog changes, including programs added after launch.
- Configure `SAFFRON_CREATION_FEE_RECIPIENT` in the backend environment for the
  fixed campaign Robinhood native ETH fee. A missing or invalid recipient prevents
  checkout. Already-issued quotes retain their recipient and exact wei amount.
- Supervise the payment watcher and automatic creator. Accepted canonical fees
  enter automatic creation without per-vault approval. External premium funding
  must be canonically complete before fixed-side entry becomes available.
- Use the backend's `ops/FULFILLMENT.md`, `ops/REFUNDS.md` and recovery runbooks.
  Refunds are paid externally and verified against the original fee; the API
  cannot sign them. Pausing intake preserves already-paid work.
- Configure the existing APR gateway and its operating owner separately. Retain
  an explicit APR unavailable state while qualification is incomplete.

The hosting provider already protects staging. Keep that arrangement, without
adding a password gate. Hosting identity must not confer application operator
permission. Live API processes never receive creator keys or broadcast methods.

## Mount and publish

Set frontend `VITE_BASE_PATH` and backend `BASE_PATH` to the same root or nested
mount. Point backend `DIST_DIR` at the combined live build. Proxy incentives API,
`rpc/robinhood` and prices before static SPA fallback. Keep genuine asset and API
404s, request limits, cookies and Origin intact. Route the APR v2 gateway with
its existing session authentication, `X-Session-ID` and unbuffered SSE.

Retain old hashed assets for open tabs. Stage the complete build, including the
`.vite/manifest.json` file, and verify it before switching the served directory.
An atomic directory switch is preferred. If publication must copy individual
files, copy assets first and the entry/marker last while intake is closed; the
check rejects the temporary inconsistency. Preserve the prior build, source
manifest, backend revision, route configuration and database backup.

Copy the separately verified ZIP to `live-apr-merge-source.zip` beside the served
installation guide if exposing its download link. Do not put that ZIP in `public/`
before creating another archive. Never include runtime settings or credentials.
Keep the interactive QA database, browser state and running services intact during
ordinary frontend publication. Its archive is not a backup of memory-only keys.

## Check the actual served mount

After producing and extracting the source ZIP, use the real target URL and its
complete mount in these commands:

```sh
node scripts/check_live.mjs <application-base-url> --expect-closed --source-manifest <source-manifest.json>
node scripts/check_browser.mjs <application-base-url> --expect-closed --source-manifest <source-manifest.json>
```

Both checks require clean committed source. The preflight verifies the marker,
mounted entry, manifest and every required asset, catalog readiness, Robinhood
chain and nonce reads, missing routes, forbidden RPC methods, Origin rejection
and unauthenticated operator rejection. It submits no quote or valid transaction.
A closed check reports `paymentReady:false`; it does not open intake or start a
worker. Only omit `--expect-closed` after an operator intentionally enables intake.

The browser check follows Home, Portfolio and Live APR through the actual host.
It creates an isolated browser with no wallet or operator login. It issues only
an ephemeral checkout capability and APR observation sessions, verifying the
browser-supplied Origin and path-scoped HttpOnly/SameSite cookie. It performs no
payment, quote, deployment, funding, claim or withdrawal.

When the hosting layer requires a session, set `SAFFRON_STAGING_STORAGE_STATE`
to a protected Playwright storage-state file obtained through the provider's
existing access flow. Use a hosting-only session: the check rejects application
wallet/operator cookies. Do not commit that file or publish browser profiles or
credentials. The script does not bypass the hosting layer or log its cookies.
An access denial is a failed check, not browser acceptance.

Set `SAFFRON_REQUIRE_APR=1` to require a non-unavailable APR display and multiple
SSE data deliveries separated in time, with the stream still open. Set
`SAFFRON_CHECK_CLIPBOARD=1` to exercise PNG copy under the browser's normal
permissions; the check never grants permissions. The report records the actual
result. A transport smoke check does not replace the comparison, baseline,
reconnect and committed-chain checks in `APR-ACCEPTANCE.md`, nor real-phone tests.

## Reproducible fixture evidence

`npm run test:release` checks root/nested mounts, preview rejection, live builds
with either appearance setting, mixed or missing files, incorrect source/mount,
HTML API fallbacks, missing recipient and accidentally inherited operator access.
With the backend's disposable test dependencies installed, build live at the
intended mount and run `npm run test:release-browser`. Set `SAFFRON_BACKEND_SOURCE`
to this repository's backend package and supply `SAFFRON_TEST_DB_*`.
`MERGE_WEBROOT` can select a separate build directory. This runs the real proxy,
API, database and EVM, verifies closed then open readiness, and creates no jobs.
Reports under `validation/release/` are explicitly fixture-only.

CI runs both root and nested served checks, the two device lifecycle journeys,
APR HTTP contracts, and fresh source extraction/builds. See
`RELEASE-ACCEPTANCE.md` for the evidence boundary and remaining launch gates.

## Compatible rollback and recovery

Pause new intake before changing routes or runtime versions. A frontend rollback
must retain the live recovery UI for accepted payments, pending transactions and
refund states. Never replace it with the simulation UI for wallets with paid work.
Keep the qualified 0.3.0 bundle as the historical recovery UI with intake closed;
there is no earlier qualified public live release to assume as a fallback.

Backend commit `903205e` is the earliest eligible code baseline from this batch:
it includes advisory capacity and canonical refund allocations, execution stops,
reconciliation and restore coverage. Earlier hard-cap or pre-refund versions are
ineligible for databases carrying these records. Eligibility is not a tested
production restore target: record an exact compatible backend/build pair and
verify it against a backup clone before launch or rollback.

Preserve schema/data, received fees, signed transaction journals, watcher cursors,
private recovery capabilities, refund manifests and allocations, audit history,
and permanently spent execution permits. Reconcile canonical outcomes before
resuming creation. An older Git revision or restored UI cannot reverse a payment,
replenish spent premium, reset a signer permit or recover QA memory-only wallets.
Follow the backend dump/restore and reconciliation procedure; do not clear
browser recovery storage or replace production data to roll back a UI.
